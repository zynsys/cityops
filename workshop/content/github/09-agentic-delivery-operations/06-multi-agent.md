# Exercise 13 — Multi-Agent Development

Multi-agent development runs specialised agents in parallel on different concerns, then coordinates the results. In this module you'll use three agents simultaneously — one on the schema, one on the API, and one on the UI — then review and integrate their outputs.

## Learning Objectives

- Understand the benefits and risks of parallel agent sessions
- Run multiple specialised agents on different layers of the same feature
- Coordinate and integrate outputs from parallel sessions
- Identify and resolve conflicts between parallel agent changes

## The Feature: Report Priority Escalation

You'll implement an escalation system: Authority Users can escalate a report's priority. This touches all three layers simultaneously — a good candidate for multi-agent work.

**What's needed:**

- Database: `escalatedAt` timestamp + `escalationReason` text on `Report`
- API: `POST /api/reports/[id]/escalate` route
- UI: Escalate button + confirmation modal on the report detail page

## Step 1 — Understand the Coordination Challenge

Before starting parallel agents, consider what could conflict:

1. All three agents need to agree on the new field names (`escalatedAt`, `escalationReason`)
2. The API agent needs to know the DB schema the migration agent produces
3. The UI agent needs to know the API endpoint the API agent builds

**Strategy**: Run the DB agent first to produce a schema definition, then share it with the API and UI agents as context.

## Step 2 — DB Agent Session

Open your **first** Copilot Chat session (Tab 1):

```
You are working on the database layer only.

Add escalation fields to the CityOps Report model in prisma/schema.prisma:
- escalatedAt: DateTime? (nullable — null means not escalated)
- escalationReason: String? (nullable — free text from the Authority User)
- escalatedById: String? (foreign key to User — who escalated it)

Create a Prisma migration using: npm run db:migrate:create -- --name add-report-escalation

Output the complete updated Report model fields AND the migration SQL so I can share them with other agents.
```

**Wait for output — copy the field definitions and migration SQL.**

## Step 3 — API Agent Session (Parallel)

Open a **second** Copilot Chat session (Tab 2) and paste the schema from Step 2:

```
You are working on the API layer only. The database team has added these fields to the Report model:
- escalatedAt: DateTime?
- escalationReason: String?
- escalatedById: String? (foreign key to User)

Implement POST /api/reports/[id]/escalate in src/app/api/reports/[id]/escalate/route.ts:
- Auth: AuthorityUser or TenantAdmin role required
- Body: { reason: string } (validated with Zod, min 10 chars)
- Sets escalatedAt to now(), escalationReason to the provided reason, escalatedById to the current user
- Scopes the report query to the session's tenantId
- Returns the updated report
- Returns 409 if already escalated

Do NOT modify the schema — that is being handled separately.
```

## Step 4 — UI Agent Session (Parallel)

Open a **third** Copilot Chat session (Tab 3) and paste the schema and endpoint info:

```
You are working on the UI layer only. The following is being added by other team members:

Database fields on Report:
- escalatedAt: DateTime?
- escalationReason: String?

API endpoint:
- POST /api/reports/[id]/escalate
- Body: { reason: string }
- Returns the updated report

Build the UI for the report detail page at src/app/reports/[id]/page.tsx:
- An "Escalate" button — visible only to AuthorityUser and TenantAdmin
- The button opens a modal/dialog asking for an escalation reason (textarea, min 10 chars)
- On submit, calls the escalate API route
- Once escalated, show an "Escalated" badge instead of the button
- If escalatedAt is set, show "Escalated on [date] by [user name]"

Do NOT modify any API routes or the schema.
```

## Step 5 — Apply the Migration

While agents 2 and 3 are running, apply the migration from agent 1:

```bash
npm run db:migrate:deploy
```

## Step 6 — Integrate and Resolve Conflicts

Once all three agents have finished:

1. **Review each output separately** — don't merge blindly
2. **Check for field name consistency** — `escalatedAt` must be spelled the same in all three layers
3. **Check imports** — the API route should import from the right place; the UI should import the Server Action, not call the API directly
4. **Check for TypeScript type coverage** — the `Report` type generated by Prisma should include the new fields automatically after `npm run db:generate`

Run Prisma client generation:

```bash
npm run db:generate
```

5. **Fix type errors** — ask any of the agents to fix type issues:

```
The Prisma-generated Report type now includes escalatedAt, escalationReason, and escalatedById. Update any types in the code you generated that were guessing at these fields.
```

## Step 7 — Integration Test

```bash
npm run dev
```

1. Sign in as an Authority User
2. Navigate to a non-escalated report
3. Click Escalate, enter a reason, confirm
4. Verify the escalated badge appears and the button is replaced
5. Verify a different council's reports cannot be escalated by your user

## What Could Go Wrong

Multi-agent development common pitfalls:

| Issue                       | Solution                                                   |
| --------------------------- | ---------------------------------------------------------- |
| Field name mismatch         | Share schema output explicitly between agents              |
| Import path conflicts       | Review all imports after integration                       |
| Duplicate utility functions | Check if a utility already exists before generating        |
| Diverging TypeScript types  | Generate Prisma client after migration before fixing types |

## Summary

You've coordinated three parallel agent sessions on different concerns and integrated their outputs into a working feature. The coordination overhead is real — but so is the speed gain for larger, well-separated features.

Key takeaways:

- Define clear boundaries before starting ("you own the API layer only")
- Share schemas and interfaces explicitly between agents to avoid divergence
- Apply migrations before fixing types so Prisma's generated types are correct
- Multi-agent works best for features with clear layer separation — not for interleaved changes
